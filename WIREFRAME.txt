Suggestion buttons are literal prompts, not placeholders:

healthCheck() probe, not an optimistic state.

4. APPROVAL PROMPT (agent is blocked until answered)
================================================================================

+------------------------------------+
| APPROVAL REQUIRED                   |
|                                    |
| The agent wants to run a command:  |
|                                    |
|   $ npm install express            |
|                                    |
| Tier: approval                     |
| "This command modifies             |
|  dependencies, files, or           |
|  repository state."                |
|                                    |
| [ Approve once ]  [ Reject ]       |
+------------------------------------+

Rules
  - Approval grants the exact command shown, once. It is not a session-wide
    permission and it does not generalise to similar commands.
  - Approvals queue when several tools are requested in one model turn; each is
    answered separately, in order.
  - Tier "blocked" never renders Approve. See docs/SECURITY.md.

Opening a recent entry restores that conversation: user turns are re-rendered as
user messages and assistant turns as activity entries. Tool-call plumbing is not
replayed, so a restored transcript never re-runs an action.


================================================================================
7. ACTIVITY PANEL SECTIONS
================================================================================

  AGENT STATUS      idle | running | stopped | limit reached, with the reason
  WORKSPACE         folder name, root path, detected project type
  LIVE ACTIVITY     streaming feed: tool starts, results, terminal output,
                    errors. Bounded in length; the full record is in the
                    terminal view and the output channel.
  PROVIDER          health dot + message per provider, switch on click

Every value here comes from a real event: postStatus() for health,
workspaceInfo for the root, gitStatus from `git status --porcelain`, and
activity events emitted by the agent loop. Nothing is synthesised for display.


================================================================================
8. RESPONSIVE BEHAVIOUR
================================================================================

  >= 1000px   sidebar | workspace | activity      all three visible
  700-999px   sidebar | workspace                 activity collapses into the
                                                 workspace header
  <  700px    workspace only                       sidebar and activity become
                                                 overlay drawers, opened from
                                                 header buttons and dismissed
                                                 by selecting outside

  The webview is registered with retainContextWhenHidden: true, so collapsing
  the view does not kill an in-flight run or lose scroll position.


================================================================================
9. STATE RULES
================================================================================

  status dot       green  = provider healthCheck() succeeded
                   red    = provider returned an error or was unreachable
                   grey   = not yet probed
  Send             enabled only when input is non-empty and the agent is idle
  Stop             visible only while a run is active
  Run ending       completed / limit reached / stopped / error are distinct
                   messages; "done" is never shown after a failure
  Empty activity   shown as an empty state, never as a fabricated entry
  Provider errors  surfaced verbatim from the provider, including HTTP status
